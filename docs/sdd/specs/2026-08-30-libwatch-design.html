ライブラリ更新ウォッチ

読者ひとりが YAML の設定ファイルでウォッチ対象を持ち、公式ブログと GitHub Releases の更新を1本のタイムラインで見る静的サイト。用語はリポジトリ直下の CONTEXT.md に従う。

Classification

architectural

Approach

設定ファイルを正本とし、ビルド時にフィードを取り込み、静的 HTML を出す。実行時サーバも DB も無い。開くたびに取り込むローカルサーバと、DB 付き常駐アプリは採らない。取り込み失敗時に前回の件を残さない。

Goals

  • 読者ひとりが、YAML の設定ファイルでウォッチ対象と更新源を持つ。
  • 公式ブログ（RSS / Atom）と GitHub Releases の更新が、1本のタイムラインに新しい順で並ぶ。
  • 各件はタイトルと公式リンク、あれば要約。本文は公式側で読む。
  • ビルドコマンドが静的 HTML を出す。読むのにアプリサーバは不要。
  • 実装は Python 3.11 以上。既定テストはネットワークに出ない。

Non-goals

  • 公開ディレクトリ、カタログ、プリセット必須、更新源の自動推定。
  • 共有ウォッチリスト、ログイン、複数人編集。
  • 本文転載、本文からの要約、生成要約。
  • ウォッチ対象ごとのページ、既読、コミットログ、ソーシャル投稿。
  • ブログ HTML のスクレイプ、任意 URL、フィードの次ページ。
  • 取り込み失敗時に前回の件を残すこと。
  • DB、常駐アプリ、非公開リポジトリ、認証付きフィード。
  • GitHub Pages への自動公開、GitHub Enterprise、gist、github.io。
  • 画面からウォッチ対象を登録する UI。

Architecture

実行時サーバは無い。読むのはビルドが書いた静的ファイルだけである。

watchlist.yml
  → GitHub Releases URL を Releases フィード URL に揃える
  → 更新源ごとにフィードを順に HTTP GET
  → 正規化（タイトル・公式リンク・要約があれば・公開日時・ウォッチ対象・種類）
  → 公開日時の新しい順にマージし、同じ公式リンクは1件にする
  → site/index.html（と付属 CSS）

GitHub Releases の URL は、そのリポジトリの Releases フィードとして扱う。リリースページの HTML は取らない。認証ヘッダは付けない。公開日時の比較は UTC で行う。タイムゾーンが無い日時は UTC とみなす。

Components

  • 設定ファイル: リポジトリ直下の watchlist.yml（UTF-8）。ウォッチリストの正本。
  • URL 解決: GitHub Releases のページ URL・リポジトリ URL・releases.atom を https://github.com/{owner}/{repo}/releases.atom に揃える。
  • 取り込み: 更新源ごとに GET し、RSS / Atom を読む。タイトル・公式リンク・要約（フィードの説明欄）・公開日時を抜く。
  • 正規化とマージ: 件を「ウォッチ対象・種類・タイトル・リンク・要約・公開日時」にし、並べて重複を潰す。
  • 静的ページ: タイムライン1画面。外部 JavaScript は使わない。
  • ビルドコマンド: リポジトリ直下で python3 -m libwatch。上記を順に実行する。
  • GitHub Actions: 任意。同じコマンドを 6 時間ごとに走らせ、site/ を artifact にする。Pages 公開はこの spec の範囲外。

Config

watchlist.yml の形:

targets:
  - name: React
    blog: https://react.dev/rss.xml
    releases: https://github.com/facebook/react/releases
  • トップレベルは targets のみ。未知のキーがあればビルド失敗。
  • targets はリスト。0 件ならビルド失敗。
  • 各要素の name は前後空白を除いたうえで空でない文字列。空ならビルド失敗。未知のキーがあればビルド失敗。表示・重複判定もこの除いた値を使う。
  • blog と releases はそれぞれ任意。どちらも無い、またはどちらも空ならビルド失敗。
  • name の重複はビルド失敗。
  • blog があるとき、値は http:// または https:// の絶対 URL でなければならない（フラグメントは無視してよい）。そうでなければビルド失敗。
  • releases があるとき、値は次節の GitHub Releases URL として解決できなければならない。できなければビルド失敗。

GitHub Releases URL

ホストは github.com のみ（大文字小文字は問わない）。スキームは http または https。クエリとフラグメントは無視する。パスは次のいずれか（末尾スラッシュはあってもよい）。

  • /{owner}/{repo}
  • /{owner}/{repo}/releases
  • /{owner}/{repo}/releases.atom

owner と repo は [A-Za-z0-9._-]+。これ以外のパス（/releases/tag/...、/tree/...、Enterprise、gist など）は設定エラーでビルド失敗。解決後のフィード URL は常に https://github.com/{owner}/{repo}/releases.atom。

Data flow

  1. watchlist.yml を読む。
  2. 各ウォッチ対象について、blog はその URL をフィードとして使う。releases は上の規則で Releases フィード URL にする。
  3. 更新源を設定ファイルに書いた順（対象の順、各対象では blog があれば先、releases があれば次）で、順に取り込む。並列にしない。
  4. フィードは返ってきた件だけ使う。次ページ（<link rel="next"> や API の pagination）は辿らない。件数上限は設けない。
  5. 各件を正規化する。
    • 公式リンクは item のリンクを、フィード URL を基準に絶対 URL にする。解決後が http:// または https:// でなければ、その件は落とす。
    • 要約は RSS description または Atom summary だけ。Atom content は使わない。本文を取りに行かない。空なら要約なし。切らない。
    • タイトルが無い、または空白だけの件は落とす。
    • 公開日時が無い件は落とす。
  6. 全件を公開日時の新しい順に並べる。同じ日時ならウォッチ対象名、その次にタイトル。比較は Unicode コードポイント順（Python の文字列比較）。
  7. 公式リンク文字列が同じ件は 1 件にする。残すのは公開日時が新しい方。同時なら種類がリリースノートの方。それも同じならウォッチ対象名が前の方、その次にタイトルが前の方。
  8. site/index.html と付属 CSS を書き出す。同じビルドの site/ 配下は揃ってから置き換える。index.html は一時ファイルに書いてからリネームする。

Page

  • 1 画面。全ウォッチ対象の更新が上の順で並ぶ。
  • 各件は、タイトル（公式リンク先）、あれば要約、ウォッチ対象名、種類（「公式ブログ」または「リリースノート」）、公開日時（UTC、YYYY-MM-DD HH:MM UTC）を出す。
  • タイトル・要約・ウォッチ対象名・種類は HTML として解釈しない。エスケープしたテキストとして出す。
  • 0 件のときは本文に「更新はまだない」と出す。
  • 失敗した更新源はページに出さない。
  • 外部 JS なし。CSS はビルドが site/ に書く 1 ファイルまで。単一カラム。

Error handling

設定（ビルド失敗、終了コード非ゼロ、site/ は触らない）:

  • ファイルが無い、UTF-8 で読めない、YAML として読めない。
  • 前節の Config / GitHub Releases URL に反する。

取り込み（その更新源だけスキップ。他は続ける。ビルドは成功してよい）:

  • 接続失敗、TLS 失敗、タイムアウト（更新源あたり 15 秒、接続と読み取りを含む）。
  • HTTP ステータスが 200 以外。
  • リダイレクトが 5 回を超える。
  • 本文が 2 MiB を超える（Content-Length が 2 MiB 超、または読み取り中に 2 MiB を超えた時点）。
  • RSS / Atom として読めない。

スキップした源は標準エラーへ 1 行ずつ出す。形式は skip source: {name} {blog|releases} {url}: {reason}。

設定は正しいが源がすべてスキップされたら、ビルド成功、空のタイムライン（「更新はまだない」）。失敗した源の件は、その回のタイムラインに出ない。書き出しに成功したあとの site/ は、今回のビルド結果だけになる。

件: タイトルまたは公式リンクが使えない件、公開日時が無い件は落とす。フィード 0 件はその源の成功・0 件。

書き出し: 一時ファイル経由で置き換える。途中失敗で壊れた index.html を残さない。設定エラーのときは既存の site/ を変えない。

Numeric defaults

  • HTTP タイムアウト: 更新源あたり 15 秒。
  • フィード取得サイズ上限: 2 MiB。
  • リダイレクト: 最大 5 回。
  • 取り込み: 順次。並列度 1。
  • GitHub Actions 間隔: 6 時間。
  • User-Agent: LibWatch/0.1。
  • 要約: 切らない。
  • フィード件数: フィードが返した件。こちらで上限なし。
  • Python: 3.11 以上。

Consuming paths

  • 読者は watchlist.yml を編集する。
  • リポジトリ直下で python3 -m libwatch を実行する。
  • site/index.html をブラウザで開く。静的ファイルとしてどこに置いてもよい。
  • 定期実行は同じコマンドを cron に載せるか、付属の GitHub Actions を使う。Actions は無くても完成する。
  • Actions を付ける場合: 6 時間ごとに python3 -m libwatch を走らせ、site/ を artifact として残す。このジョブはネットワークに出てよい。

Testing

既定テストはネットワークに出ない。フィードと設定はフィクスチャ。HTTP はテストから差し込める。

  • 設定が無い・YAML として読めない・対象 0 件・対象名が空・更新源がゼロ・未知キー・不正 URL・GitHub Releases URL からリポジトリが取れない・name 重複 → ビルド失敗、site/ 非更新。
  • GitHub Releases のリポジトリ URL・/releases・releases.atom（末尾スラッシュありなし、ホストの大小、http）→ 同じ https://github.com/{owner}/{repo}/releases.atom。
  • 相対リンクは絶対 URL になる。javascript: などは件として落ちる。
  • 要約は RSS description または Atom summary だけ。Atom content は要約に使わない。タイトル・公式リンク・公開日時が無い件は落ちる。
  • 並びは公開日時の新しい順。同タイムはウォッチ対象名、その次にタイトル。
  • 同じ公式リンクは 1 件。同時ならリリースノートを残す。
  • 取り込み失敗はその源だけスキップし、他の件は残り、終了コード 0。標準エラーに skip 行が出る。ページに失敗源は出ない。
  • 源がすべてスキップされたら空のタイムラインで終了コード 0。
  • HTML にタイトルと公式リンクがある。本文全体は出さない。テキストはエスケープする。
  • 空のときは「更新はまだない」。
  • 書き出し失敗のあと、壊れた HTML が残らない。
  • 既定テストランナーはネットワークに接続しない。
